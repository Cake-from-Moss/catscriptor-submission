# Локальная оценка Catscriptor

## Статус и назначение

Инструменты issue #11 работают на компьютере и не входят в APK. Они принимают
настоящий экспорт Catscriptor без изменения Android-контракта. Нет обращений
к сети, загрузки моделей или инференса при оценке. Интернет нужен только для
первоначальной установки Python-зависимостей; дальше оценка автономна.

**Реального размеченного набора русских диалогов пока нет.** Репозиторные
искусственные JSON проверяют алгоритмы, а не ASR. Имеющиеся Android-тестовые
сигналы и smoke-test ASR не заменяют диалоги с проверенными спикерами,
перекрытиями, лицензией и ручными таймкодами. Результаты ниже не следует
публиковать как качество модели или как окончательное закрытие issue #11.

Для получения реальных данных готов [комплект записи A/B/C](../tests/data/evaluation/recording-kit/README.md):
сценарии людям, Android-инструкция, TSV для ручной разметки, шаблон метаданных
и локальные команды `python -m tools.evaluation.dataset convert|inspect|validate`.
Валидатор проверяет WAV/контрольные суммы/структуру/документы о правах, но не
способен подтвердить содержание речи или юридическую действительность согласия.

Требования команды: весь инференс на Android, локальная LLM обязательна,
в оценочном APK модели bundled. Эти инструменты не меняют данные требования,
модели, архитектуру приложения или экспорт. Известные веса критериев хакатона:
ASR 40, диаризация 25, время 10, скорость 10, UX 10, защита 5.
Точный алгоритм судейского сравнения, collar, устройство и лимит APK неизвестны;
наша методика не объявляется официальной формулой начисления баллов.

## Установка и быстрый старт

Нужен Python **3.10+** (выполнение проверено на 3.11.14/macOS arm64);
Android SDK не нужен. Linux/Windows и Python 3.10 отдельно на этом компьютере
не запускались. Код использует переносимые pathlib/subprocess; JSON-файлы
и вывод CLI явно UTF-8, включая перенаправление вывода в Windows.
Зависимости вместе с транзитивными версиями зафиксированы в
`requirements-evaluation.txt`. На другой версии Unicode/Python возможны отличия
нормализации редких символов: версии Python, Unicode, jiwer и RapidFuzz записаны
в отчёт. Для идентичных результатов используйте одинаковое окружение и исходники.

```bash
python3.11 -m venv tools/evaluation/.venv
source tools/evaluation/.venv/bin/activate
python -m pip install -r requirements-evaluation.txt
python -m pytest tools/evaluation/tests -q
python -m tools.evaluation.evaluate \
  --reference tests/data/evaluation/reference.json \
  --hypothesis tests/data/evaluation/hypothesis.json \
  --output /path/to/report.json
```

В PowerShell активация: `tools/evaluation/.venv/Scripts/Activate.ps1`;
вместо `python3.11` при создании окружения можно использовать `py -3.10`.
Зависимости pytest для Python 3.10 и Windows зафиксированы условными маркерами.

Для примера замените `/path/to/report.json` на существующий доступный каталог.
Ожидания для этих **искусственных** данных: WER 0.25, DER 0, MAE 0 мс,
RTF отсутствует. Можно запускать непосредственно
`python tools/evaluation/evaluate.py ...`, в том числе из другого каталога.
Код возврата: 0 — оценка выполнена, 2 — ошибка аргументов/входа/записи отчёта.
Высокая ошибка распознавания сама по себе не является ошибкой запуска.

Пакетный запуск:

```bash
python -m tools.evaluation.evaluate \
  --manifest tests/data/evaluation/manifest.json \
  --collar-ms 0 --tolerance-ms 100 250 500 \
  --output /path/to/batch-report.json
```

Формат manifest (пути относительно самого manifest; ID уникальны):

```json
{
  "recordings": [
    {
      "id": "dialogue-a",
      "reference": "a/reference.json",
      "hypothesis": "a/catscriptor.json",
      "measurement": "a/measurement.json"
    }
  ]
}
```

`measurement` необязателен. Входы не перезаписываются отчётом. Существующий
отчёт по `--output` заменяется. Пустой manifest запрещён, пустой transcript
допустим. При некорректной записи пакет целиком отклоняется, а не молча
оценивается на оставшихся данных. Отчёт содержит настройки, SHA-256 входов,
тексты до/после нормализации, перестановки спикеров, пары реплик, все
несопоставленные индексы и агрегированные счётчики. Индексы начинаются с нуля.
Текстовый вывод краткий, полный аудит — в JSON. Отчёт тоже может содержать
чувствительную информацию: храните локально наравне с аудио.

## Валидация

Эталон и результат используют **одинаковый строгий экспортный формат**:

```json
{"transcript":[{"speaker_id":"speaker_1","start_ms":1250,"end_ms":4380,"text":"Добрый день!"}]}
```

Разрешены только эти поля и верхний объект `transcript`. Отвергаются лишние
и отсутствующие поля, повторяющиеся JSON-ключи, NaN/Infinity, неверные типы,
float/bool вместо целых миллисекунд, отрицательное начало, нулевая/отрицательная
длительность, нарушение порядка по началу. Нужен `speaker_[1-9][0-9]*`, как
в `Segments.kt`; строки и пустые строки текста допустимы. Реплики с одинаковым
началом и пересечения разрешены. Python int не теряет точность Kotlin Long,
временная шкала не преобразуется в float при DER и matching.

Дополнительные метаданные, лицензия и слова хранятся **отдельно**, а не добавляются
в JSON экспорта. Экспорт не содержит пословных меток; пословную точность данный
инструмент не вычисляет. Если передана длительность, выход эталона за её пределы
считается ошибкой разметки. Выход предсказания не обрезается: это потенциальный
false alarm. Без длительности используется вся объединённая шкала интервалов.

## WER

Тексты реплик соединяются переводом строки в экспортном порядке (по началу).
Нормализация одинакова для обеих сторон:

1. Unicode NFC — не NFKC, не транслитерация.
2. `lower()`.
3. `ё → е`, кроме диагностического режима `--keep-yo`.
4. Каждый Unicode-символ категории `P*` заменяется **пробелом**: `кот,пёс`
   становится `кот пес`, а не `котпес`. Дефисы и апострофы тоже разделяют слова.
5. Пробелы, табуляции, переводы строк схлопываются, края обрезаются.

Не переставляются слова; нет лемматизации, исправления опечаток, удаления
слов-паразитов, раскрытия чисел и сокращений. Символы вне пунктуации, например
`+`, сохраняются. Поэтому `два` и `2` различаются. Такие решения не скрывают
ошибки ASR, но дефисные слова теряют различие написания; сравнивайте варианты
моделей с одной конфигурацией.

`jiwer.process_words` 4.0.0 выполняет выравнивание и возвращает S, D, I.
`N` — число слов нормализованного эталона. WER = (S+D+I)/N, может быть больше 1.
При N=0 и I=0 возвращаем 0, при N=0 и I>0 — **null**, вставки сохраняются.
Это явная конвенция инструмента, отличающаяся от jiwer 4, который возвращает
число вставок как WER пустого эталона. Пустой результат при N>0 даёт WER=1.

Корпусный WER = (ΣS+ΣD+ΣI)/ΣN, а не среднее WER записей. Вставки из записей
с пустым эталоном входят в числитель. Для полностью пустого корпуса применяется
та же конвенция null/0.

WER здесь не speaker-attributed и не permutation-invariant по словам. При
одновременной речи порядок слов в линейной записи неоднозначен: даже верное
распознавание с другой сегментацией/порядком начала может увеличить WER.
Для воспроизводимости эталон фиксирует один порядок; это ограничение нужно
учитывать отдельно, а не исправлять сортировкой слов по тексту.

## DER: непрерывная временная оценка

Собственная реализация использует интервальные события и точное максимальное
взвешенное паросочетание (венгерский алгоритм). Это стандартная декомпозиция DER,
а не сравнение строк speaker_id и не доля совпавших реплик. Тяжёлый стек
pyannote/torch для этой задачи не требуется. Реализация проверена вручную
рассчитываемыми примерами, независимым дискретным перебором перестановок
и перекрёстно с pyannote.metrics 3.2.1 (606 сравнений компонентов, seed=11).

Время делится по всем началам/концам на полуоткрытые интервалы `[a,b)` с
постоянным множеством активных спикеров эталона R и результата H.
Перекрывающиеся реплики **одного** спикера объединяются логически (спикер
считается один раз); разных спикеров — учитываются независимо. Для каждой
пары спикеров суммируется время совместной активности на оцениваемой шкале.
Глобальное взаимно-однозначное соответствие H→R максимизирует это время для
всей записи, тем самым минимизируя confusion. Лишние спикеры остаются без пары;
соответствие не переопределяется на каждой реплике. Нулевые пары не сохраняются.
При равных оптимумах используется детерминированный порядок строковых ID.

Для интервала длительностью Δ с C правильно сопоставленными активными спикерами:

- missed speech = Δ × max(0, |R|−|H|);
- false alarm = Δ × max(0, |H|−|R|);
- speaker confusion = Δ × (min(|R|,|H|)−C);
- знаменатель = Δ × |R|.

DER = сумма трёх ошибок / суммарное эталонное **speaker-time**. Поэтому две
секунды двух одновременных спикеров дают четыре speaker-секунды. Поле `*_ms`
в DER хранит speaker-миллисекунды, а не просто длительность аудио.
DER может превышать 1. Нет эталонной речи и есть false alarm → null;
нет ошибок и знаменатель нулевой → 0 (смотрите также сам знаменатель).
Общий DER складывает компоненты и знаменатели записей; перестановка выполняется
независимо для каждой записи, ведь speaker_1 разных записей — не один человек.

По умолчанию collar = 0. `--collar-ms N` исключает из **всей** оценки DER
объединение областей ±N мс вокруг каждого начала и конца эталонной реплики
(с обрезкой слева в нуле). Исключаются и числитель, и знаменатель, и данные
для выбора перестановки. Это N с каждой стороны, а не суммарная ширина N.
Перекрывающаяся речь оценивается, `skip_overlap` не применяется. Короткие
реплики не фильтруются, короткие паузы не склеиваются. Большой collar может
полностью исключить короткую реплику — нулевой DER с нулевым знаменателем
не доказательство качества; публикуйте collar и speaker-time.

## Таймкоды: matching и ограничения

Для диагностики границ берётся глобальная перестановка спикеров **без collar**,
чтобы короткие реплики не исчезали. Она записывается отдельно в `boundaries`.
Между эталонными и предсказанными репликами создаются рёбра только при
совпадении сопоставленного спикера и **положительном временном пересечении**.
Вес — точная длительность пересечения в мс. Венгерский алгоритм максимизирует
сумму пересечений с ограничением «одна реплика — не более одной пары».
Никакого сопоставления по порядковому номеру или по самому тексту нет.
Текстовая ошибка не должна определять измеряемую точность времени.

Для каждой пары сохраняются signed ошибки `predicted−reference` начала/конца.
MAE начала и конца — средние абсолютные ошибки; MAE границ — сумма абсолютных
ошибок обоих концов / (2 × число пар). Допуски включительные (`<=`), по умолчанию
100, 250, 500 мс; задаются `--tolerance-ms`. Это **наши диагностические пороги**.

`within_fraction` — доля границ **сопоставленных** реплик в допуске;
`reference_boundary_coverage` — число таких границ / (2 × все эталонные реплики).
Последняя дополнительно штрафует отсутствие пары. Все несопоставленные индексы
и их количество видны в отчёте. При отсутствии пар MAE и доля пар равны null,
не нулю. Корпусные MAE взвешены количеством пар, а не количеством записей.
Нулевой MAE при множестве пропущенных реплик не означает точных таймкодов
всего файла: MAE вообще не описывает интервалы без пары. Смотрите coverage
и unmatched вместе с MAE; coverage также выводится в терминал.

Split/merge не маскируется: при разделении эталонной реплики выбирается только
одна часть, остальные предсказания остаются без пары; при объединении — только
одна эталонная реплика получает пару. Даже идеальные слова с другой сегментацией
могут дать плохие границы. Непересекающиеся или ошибочно сопоставленные по
спикеру реплики не получают искусственных расстояний: они идут в unmatched.
Это не универсальная метрика word alignment и не many-to-many scoring.
При нескольких равнооптимальных перестановках спикеров/реплик MAE зависит от
выбранного детерминированного оптимума: проверяйте пары при разборе ошибок.

Паросочетание требует O(n³) времени и O(n²) памяти (n — максимум числа реплик
в одной записи); для очень длинных, сильно фрагментированных записей это
ограничение. DER использует события, а не массив по каждой миллисекунде,
поэтому большие абсолютные метки сами по себе не увеличивают число шагов.

## RTF и условия эксперимента

RTF = реально измеренное время обработки / длительность аудио, в секундах.
Для одиночного запуска передайте `--measurement measurement.json`.
Следующий JSON — **пример формата, не результат эксперимента**:

```json
{
  "audio_duration_seconds": 60,
  "processing_time_seconds": 30,
  "model": "GigaAM",
  "variant": "v3 CTC",
  "quantization": "int8",
  "device": "заполнить точную модель телефона и SoC",
  "threads": 4,
  "notes": "заполнить границы измерения, состояние устройства и APK commit"
}
```

Такой ввод арифметически даст 0.5, но CLI не способен подтвердить происхождение
времени. Вносите **только измерения на настоящем Android-устройстве**, не время
Python-оценки и не эмулятор. Ноль допустим как явно переданное измерение,
но неизвестное время — отсутствие поля или null. Длительность обязательна
и строго положительна. Для времени обязательны model, variant, quantization,
device, threads; дополнительное `peak_memory_mb` необязательно.

Рекомендуемые границы: монотонный таймер от запуска обработки импортированного
аудио до готового исправленного LLM результата, включая decode/VAD/ASR/диаризацию/
merge/LLM и загрузку моделей, но без пользовательского выбора файла и экспорта.
Любые иные границы явно фиксируйте в notes и не сравнивайте как одинаковые RTF.
Отдельно укажите холодный/тёплый запуск, Android/SoC/RAM, питание, нагрев,
число потоков каждого backend, версии всех моделей, квантизации и APK commit.
Повторите минимум три раза, сохраняйте каждый запуск отдельно, не смешивая
повторы в один «независимый» корпус WER. Пиковую память фиксируйте с методом
измерения (например, PSS и частота выборки), не подменяйте размером модели.

Корпусный RTF = сумма processing_time / сумма audio_duration **измеренных**
записей; `measured_recordings` показывает покрытие. Это не простое среднее RTF.
Агрегат не обеспечивает сопоставимость разных устройств/моделей — manifest
для одного сравнения должен содержать один экспериментальный профиль.

Непредставимый в конечном float RTF или переполнение суммарного времени
отвергается с ошибкой входа, а не записывается как Infinity/NaN.

## Необязательная независимая проверка DER

Не устанавливайте это окружение для обычной оценки. Для повторения cross-check
нужен отдельный Python 3.11 venv с более тяжёлыми, зафиксированными зависимостями
(без моделей, torch и аудио):

```bash
python3.11 -m venv /path/to/der-check-venv
/path/to/der-check-venv/bin/python -m pip install -r tools/evaluation/requirements-crosscheck.txt
/path/to/der-check-venv/bin/python -m tools.evaluation.crosscheck_der --cases 200 --seed 11
```

Проверяется каждый компонент и знаменатель с допуском 1e-6 мс: 200 случайных
пар разметок и два пустых крайних случая × collar 0/100/250 мс = 606 сравнений.
Есть разные числа спикеров, наложения, короткие интервалы, пропуски и FA.
Конвенция DER при нулевом знаменателе сравнивается не как отношение, а через
компоненты: pyannote может возвращать infinity, мы используем null.

Обнаружены два важных различия соглашений, не ошибка нашей формулы:
pyannote задаёт **полную ширину** collar (передаём 2N), а наивная передача
пересекающихся треков одного спикера в pyannote 3.2.1 считает их дважды.
Поэтому cross-check объединяет их через библиотечный `Annotation.support()`.
Чтобы не потерять исходные границы при collar, его исключение сначала вычисляет
сама pyannote через `extrude` на исходной разметке; затем она оценивает support
с полученной UEM и нулевым повторным collar. Наша реализация не импортирует
и не использует код pyannote для подсчёта своих метрик.

## Протокол реального набора A/B/C

Самый безопасный воспроизводимый источник — собственная запись команды с
согласием участников. **Сейчас такие записи не предоставлены и не создавались.**
Не использовать синтез речи как доказательство качества реальных диалогов,
не придумывать расшифровку и не превращать приблизительные метки в проверенные.

1. До записи получить согласие всех участников на запись, локальную обработку,
   хранение и отдельно публикацию аудио/разметки. Без права публикации хранить
   вне Git в согласованном закрытом каталоге. Для публикации выбрать явную
   лицензию с правообладателями (например, CC BY 4.0 при их согласии), сохранить
   текст согласия/лицензии, атрибуцию и дату. Не обещать анонимность голоса.
2. Подготовить три естественных русских разговора о котах по 1–3 минуты, без
   чтения заранее готовой расшифровки:
   - A: два участника, тихая комната, различимые голоса, минимум перебиваний.
   - B: два-три участника, быстрые короткие ответы, заметные паузы и смены ролей.
   - C: два-три участника, безопасный бытовой шум без чужих голосов/музыки,
     минимум одно реальное наложение речи и несколько коротких реплик.
3. Зафиксировать микрофон/телефон, расположение участников, формат, частоту,
   каналы, условия шума. Сохранить неизменённый оригинал и SHA-256; локально
   получить рабочий PCM WAV (16 кГц mono), сохранив команду/версию конвертера
   и SHA-256 производного файла. Не менять темп и не обрезать начало без записи
   преобразования. Экспорт ASR и эталон должны относиться к одному файлу/нулю.
4. В локальном редакторе со спектрограммой/волной (Audacity, ELAN и т. п.) вручную
   прослушать весь файл, транскрибировать **реально слышимые** слова, включая
   повторения/оговорки. Не брать ASR за проверенный эталон. Зафиксировать политику
   междометий и неразборчивой речи; для основного небольшого набора перезаписать
   неразборчивый фрагмент либо оставить запись вне оцениваемого набора. Скрытого
   вырезания неудобных интервалов в данном scorer нет.
5. Назначить speaker_1, speaker_2, ... в порядке первого появления, подтвердить
   постоянство личности на всём файле. Перекрытие размечать отдельными репликами
   с пересекающимися интервалами. Начало/конец — первый/последний речевой звук,
   не середина паузы. Один непрерывный ход одного участника — одна реплика;
   заранее принять единый порог паузы, например 500 мс, и записать его в метаданные.
   Это политика разметки, **не встроенное слияние интервалов scorer**.
6. Уточнить границы повторным прослушиванием и визуальной проверкой, округлить
   до целых миллисекунд, отсортировать по start_ms; для равного начала принять
   фиксированный порядок speaker_id и не менять его между экспериментами.
   Второй разметчик независимо проверяет текст, спикеров и каждую границу,
   разногласия решаются совместным прослушиванием. Сохранить имена/псевдонимы
   разметчиков, инструмент/версию, дату, неопределённость и журнал исправлений.
   Только после этого ставить статус `verified`.
7. Хранить рядом `audio.wav`, `reference.json`, `metadata.json`, `LICENSE.txt`,
   затем `catscriptor.json`, `measurement.json`. Метаданные не передаются как
   transcript. Для каждого файла: duration (точное число сэмплов / sample rate),
   source, rights holder, license, consent status, hashes, scenario, speakers,
   annotation policy, verification status. При публичном внешнем источнике ещё
   URL, версия/дата получения и доказательство прав на конкретное аудио, а не
   только лицензия кода репозитория. Неподтверждённые материалы не скачивать.
8. Пословные интервалы — необязательный отдельный `words.json` с ручной проверкой;
   без них записать `word_timestamps: unavailable`. Не делить реплику равномерно
   и не выдавать токенные точки ASR за эталонные границы слов.
9. Передать второму разработчику разрешённым способом неизменённые файлы с
   SHA-256, согласованной лицензией и manifest. Если набор закрытый, описать
   процедуру доступа; публичная воспроизводимость тогда ограничена.
10. Проверить эталон CLI запуском reference против самого себя (WER/DER/MAE=0,
    кроме отсутствующих пар у пустого файла); затем импортировать **тот же**
    audio.wav в настоящий APK, экспортировать JSON и оценить с измерением.
    Заполнить [TEST_RESULTS.md](TEST_RESULTS.md), приложить отчёты/коммиты.

Протокол не заменяет сами файлы и не гарантирует одинаковых разговоров при
повторной записи. Воспроизводимый эксперимент начинается с зафиксированного
аудио, прав, проверенной разметки, контрольных сумм и версии инструмента.
