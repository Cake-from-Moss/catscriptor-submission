# Локальная LLM-коррекция транскрипции (issue #7)

## Цель

Этап `CORRECT_TEXT` получает текст реплики от GigaAM и исправляет его локальной LLM:
пунктуация, заглавные буквы, очевидные ошибки распознавания слов. Спикер, `start_ms`,
`end_ms` и порядок реплик не меняются — LLM возвращает только строку текста,
вызывающий код применяет `utterance.copy(text = correctedText)`.

LLM **не** имеет права: придумывать слова и факты, менять смысл, удалять или добавлять
отрицания, заменять имена и числа без оснований, склеивать или переставлять реплики,
пересказывать. При сомнении предпочитается исходный текст.

## Модель

**Два уровня (настройки → «Пунктуация и правка»):** «Выкл», «Быстрая» — Qwen2.5-0.5B (`llm-fast-manifest.properties`), «Умная» — Qwen2.5-1.5B (`llm-manifest.properties`, по умолчанию). Обе модели лежат в APK; одновременно в памяти только одна. Таблица ниже описывает «Умную»; промпт и `CorrectionReconciler` подбирались на 1.5B, качество «Быстрой» не измерено.

| Параметр | Значение |
|---|---|
| Модель | **Qwen2.5-1.5B-Instruct** |
| Квантование | Q4_K_M (GGUF) |
| Размер файла | 1 117 320 736 байт (~1065 МиB) |
| Источник | <https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF> (официальный релиз Qwen) |
| Ревизия | `main`, файл `qwen2.5-1.5b-instruct-q4_k_m.gguf` |

### Почему эта модель

Сравнивались (все — Apache-2.0, с GGUF): Qwen2.5-0.5B-Instruct (491 МB Q4_K_M),
Qwen2.5-1.5B-Instruct (1065 МB), Qwen3-0.6B (официально только Q8_0, 610 МB;
Q4_K_M — только комьюнити-сборка QuantFactory), Vikhr-Qwen-2.5-0.5b-Instruct
(380 МB, русский SFT, ~900 загрузок, мало проверена).

Выбор 1.5B — осознанный приоритет качества коррекции над скоростью и размером APK:
задача «править текст, не добавляя фактов» чувствительна к следованию инструкциям,
а разрыв 0.5B→1.5B по этому параметру большой. Риски приняты: APK растёт до ~1,4 ГB,
на флагманском ARM64 ожидается ~13 ток/с (~6 с/реплика). Замер на устройстве обязателен
(см. «Измерения»). Резервный вариант при нехватке RTF/размера APK — Qwen2.5-0.5B-Instruct
(та же схема манифеста, замена одного файла).

Qwen3-0.6B отклонён: режим thinking включён по умолчанию, C API `llama_chat_apply_template`
не принимает kwargs шаблона, `/no_think` на 0.6B ненадёжен, а малые кванты только
у сторонней сборки. Qwen2.5 — стабильный ChatML без шаблонных рисков.

## Inference engine

| Параметр | Значение |
|---|---|
| Движок | llama.cpp, пин на релиз **v0.9.0** (commit `cd959bae99ff4bed22bef2604f45241c09bbb8c8`) |
| Источник | тарболл релиза, SHA-256 в `dependencies/llama-cpp.properties` |
| Лицензия движка | MIT (`app/src/main/assets/third-party/llama.cpp-LICENSE`) |
| Сборка | vendored в `dependencies/llama.cpp` (в git не коммитится), `add_subdirectory` в `app/src/main/cpp/CMakeLists.txt` |
| Конфигурация | CPU-only, статическая линковка в `libllm-jni.so`, C API (`LLAMA_BUILD_COMMON=OFF`) |

Критичные флаги CMake: `GGML_NATIVE=OFF` (кросс-компиляция), `GGML_CPU_KLEIDIAI=OFF`
(иначе CMake скачает исходники KleidiAI через FetchContent при конфигурации — нарушение
воспроизводимости), `GGML_OPENMP=OFF`, `GGML_LLAMAFILE=OFF`, `GGML_BACKEND_DL=OFF`,
`LLAMA_OPENSSL=OFF`. Релиз пинится, а не master: API между v0.8.0 и v0.9.0 для
используемых функций идентичен; master не гарантирует стабильности.

Публичный C API v0.9.0 важен одним переименованием: `llama_kv_cache_clear` удалён,
очистка KV между запросами — `llama_memory_clear(llama_get_memory(ctx), true)`.
Отмена decode — `ggml_abort_callback` (в `llama_context_params`) плюс мягкая проверка
флага между токенами; отмена загрузки — `llama_progress_callback`, возвращающий false.

## Архитектура

```
Utterance ──> LlamaTextCorrector (TextCorrectionBackend)
                ├─ CorrectionPrompt  : системная инструкция + сборка user-сообщения
                ├─ CorrectionGuard   : допустимость правки (отклонение → исходный текст)
                └─ LlamaBridge ──> LlamaNativeBridge (JNI) ──> llm-jni.cpp ──> llama.cpp
Corrected text (только строка; метаданные реплики не трогаются)
```

- `domain/pipeline/CorrectionPrompt.kt` — чистый JVM: системный промпт, сборка сообщения,
  `sanitize` сырого вывода (code fences, обрамляющие кавычки, служебные подписи, пробелы).
- `domain/pipeline/CorrectionGuard.kt` — чистый JVM: проверка допустимости. Все пороги —
  в `CorrectionGuardConfig` (конфигурируемо, покрыто тестами).
- `native/models/LlamaTextCorrector.kt` — реализация `TextCorrectionBackend`: ленивая
  загрузка модели один раз на этап, отмена, `close()` с освобождением.
- `native/models/LlamaBridge.kt` — интерфейс нативного бэкенда (фейкается в JVM-тестах).
- `native/models/LlamaNativeBridge.kt` — `System.loadLibrary("llm-jni")`, external funs.
- `app/src/main/cpp/llm-jni.cpp` — сессии (create/load/generate/cancel/unload), UTF-8
  конвертеры (JNI MUTF-8 не годится для суррогатов/эмодзи), chat template, decode-цикл.

## Управление памятью

- GGUF копируется из assets в `noBackupFilesDir/models/<id>/` через `BundledModelStore`
  (проверка SHA-256, атомарный move, повторно не копируется). Модель мапится из файла
  (`LLAMA_LOAD_MODE_AUTO` → mmap, `MAP_POPULATE` при загрузке — разовый I/O-всплеск).
- `n_ctx = 1024`, `n_batch = n_ubatch = 512`, `n_threads = n_threads_batch = min(4, число ядер)`
  (`defaultLlamaThreads`: лишние потоки на 1–2 ядрах замедляют генерацию), K/V F16. Пиковая добавка к файлу модели — порядка 0,3–0,5 ГB (KV + буферы).
- Модель держится в пределах этапа `CORRECT_TEXT`, затем `close()`: сначала `cancel`,
  потом ожидание нативного mutex сессии, `llama_free(ctx)`, `llama_model_free(model)`.
  Освобождение параллельно с активным decode не выполняется никогда.
- В начале каждого запроса — `llama_memory_clear`: реплики не загрязняют друг друга.

## Промпт

Системная инструкция (полностью — в `CorrectionPrompt.SYSTEM`): переписать текст слово
в слово, не удалять, не добавлять и не переставлять слова (даже повторы и паразиты);
расставить пунктуацию и регистр; исправлять слово только при явной ошибке в 1–2 буквах;
отрицания, числа и имена не трогать; вернуть только текст. В конце — один пример.

Формулировка подобрана прогоном той же Qwen2.5-1.5B Q4_K_M (llama-cpp-python, ChatML,
жадно, как в JNI) на 10 репликах без пунктуации (пример — `CorrectionReconcilerTest`).
Прежняя редакция («исправь очевидные ошибки, не пересказывай») сохранила все слова
в 4 из 10 реплик: выкидывала хвосты («…кормил кота или опять забыл» → «…кормил кота.»),
схлопывала повторы, переставляла слова и подменяла местоимения («он» → «Барсик»).
Новая — в 6–7 из 10. Опечатки ASR («халадильника») модель 1.5B почти не исправляет
ни в одной редакции: основной её вклад — пунктуация и регистр.

User-сообщение по умолчанию — только текст реплики (без speaker id и таймкодов:
они не помогают правке и провоцируют переписывание). Контекст предыдущей реплики
поддержан опционально (`buildUserMessage(text, previous)`), по умолчанию выключен.

## Sampling

- По умолчанию жадное декодирование (`temperature = 0`, детерминизм важнее разнообразия).
- `presence_penalty = 0` (сэмплер штрафа в цепочку не добавляется). Раньше было 0,3:
  ответ коррекции обязан повторять слова, запятые и частицы исходника, а штраф толкал
  модель их заменять. Зацикливание ограничено потолком токенов и guard.
- Реплика длиннее 40 слов правится почти равными фрагментами (`LlamaConfig.maxChunkWords`);
  каждый фрагмент проверяется guard отдельно. Делится только текст для LLM — таймкоды
  и границы реплик не меняются. Раньше потолок `min(192, слова*3 + 32)` обрезал ответ
  на реплику длиннее ~60 слов, и хвост терялся.
- Потолок выхода на фрагмент: `maxTokens = min(192, слова*4 + 32)`.
- Остановка по EOG (`<|im_end|>` для Qwen2.5 ChatML) или по потолку токенов.
- Конфигурируемо через `LlamaConfig` (temp>0 включает top_k=40/top_p=0.9/temp).

## Защита от галлюцинаций

`CorrectionGuard.verify(original, candidate)` — консервативный фильтр; при отказе
возвращается исходный ASR-текст. Проверки (порядок = дешёвые и критичные первыми):

1. непустой исходник и кандидат;
2. маркеры meta-commentary («исправленный текст», «могу помочь», «надеюсь,»…);
3. цифры: мультимножества цифровых последовательностей обязаны совпадать
   («15 30» и «15:30» эквивалентны — сравниваются по последовательностям цифр);
4. отрицания: число вхождений каждого слова из списка не должно измениться
   (ни удаление, ни добавление);
5. рост строки по символам ≤ 1,4× + 24 символа люфта (пунктуация);
6. число предложений не растёт более чем на 2;
7. добавленные слова ≤ 3 + 15% длины исходника;
8. сохранность слов исходника по LCS ≥ 60%;
9. словое редакционное расстояние ≤ 35% от длины исходника (ранний выход по потолку).

Сравнение идёт по нормализованным словам (регистр, ё→е, пунктуация убраны), поэтому
«привет как дела» → «Привет, как дела?» проходит, а «я не приду завтра» → «Я приду
завтра.» и «встреча в 15 30» → «Встреча в 17:30.» отклоняются.

### Пословное согласование (`CorrectionReconciler`)

Глобальные пороги пропускали правку целиком: при «до 35% правок» модель могла выкинуть
2 слова из 12 или подменить слово, и это попадало в экспорт. Поэтому прошедший проверки
кандидат не применяется как есть: итоговый текст собирается выравниванием слов ASR и LLM
(Левенштейн по словам + склейка/разбиение без изменения букв):

| Операция LLM | Что попадает в итог |
|---|---|
| совпадение слова | слово LLM (регистр) с её пунктуацией |
| замена, близкая по написанию | слово LLM: «вакзал» → «вокзал», «малако» → «молоко» |
| замена другим словом | слово ASR: «сидит» → «лежит», «ты» → «я», «он» → «Барсик» отклоняются |
| склейка/разбиение без изменения букв | вариант LLM: «по этому» → «поэтому» |
| удаление слова | слово ASR возвращается на место |
| добавление слова | выбрасывается, знаки препинания вокруг сохраняются |

«Близко по написанию» — посимвольное расстояние ≤ 1 для слов до 5 букв, ≤ 2 до 9,
≤ 3 длиннее; слова короче 3 букв, числа и защищённые слова (отрицания, «да», «уже»,
«ещё», «был/была»…) не меняются никогда. В итоге LLM не может ни потерять распознанное
слово, ни выдумать новое: WER меняется только за счёт близких по написанию исправлений.
Начало предложения после `.`/`!`/`?` получает заглавную букву.

Фильтр **не гарантирует** отсутствие галлюцинаций: он не понимает смысл. Он консервативен
— лучше отклонить полезную правку, чем пропустить фабрикацию. Ошибочно отклонённая
правка не вредит транскрипту (текст остаётся исходным).

## Длинные записи

- Модель загружается один раз на этап; реплики обрабатываются последовательно.
- Каждая реплика — отдельный запрос с очисткой KV; длинный контекст не накапливается.
- Промпт длиннее контекста отклоняется нативно; гвард отсекает вздутый вывод.
- Пустой текст реплики: генерация не вызывается, возвращается пустая строка.

## Отмена

- До загрузки: `ensureActive` до нативных вызовов; сессия уже создана, `close()` чистит.
- Во время загрузки: `llama_progress_callback` → false при выставленном флаге отмены.
- Во время генерации: Kotlin-watcher (`awaitCancellation`) немедленно зовёт
  `bridge.cancel`; `ggml_abort_callback` обрывает текущий `llama_decode`,
  проверка флага между токенами завершает цикл; частичный вывод отбрасывается,
  корутине уходит `CancellationException`.
- `close()` во время генерации: `cancel` → ожидание нативного mutex → освобождение.

## Упаковка в APK и офлайн

GGUF и LICENSE лежат в `app/src/main/assets/models/qwen2.5-1.5b-instruct-q4_k_m-2026-11-07/`
(`noCompress` покрывает `gguf` — без распаковки при чтении). Перед сборкой
`verifyBundledModels` проверяет SHA-256 и размеры по `llm-manifest.properties`;
`BundledModelSpec.readLlm()` требует ровно один `.gguf` и `LICENSE` — проверки VAD/ASR
не ослаблены. `scripts/prepare_models.py` скачивает модель, лицензии и исходники
движка с верификацией хэшей. Приложение не запрашивает `INTERNET`; первый запуск
работает в авиарежиме.

## Интеграционный статус

Встроено в production-путь: `DiarizedDraftRunner` (AudioProcessingService) выполняет
`CORRECT_TEXT` через `LlamaTextCorrector` после слияния реплик; результат уходит в
`AudioProcessingState.transcript`, контроллер переводит запись в `RecordingStatus.Ready`,
репозиторий отдаёт готовый транскрипт (спикеры + исправленный текст) на экран транскрипта
с правками реплик и имён спикеров. `PipelineOrchestrator` остаётся тестируемой моделью
полного пайплайна; порядок «диаризация до ASR» сознательно сохранён (#6).

## Измерения (vivo V2538, Snapdragon 4 Gen 2, Android 16, arm64-v8a, 12 ГБ RAM)

Qwen2.5-1.5B-Instruct Q4_KМ, llama.cpp v0.9.0, n_ctx=1024, 4 потока, greedy,
веса в RAM (`load_mode=NONE`), debug APK с `-O2` для нативного кода:

| Этап | Время (сэмпл ~15 с) |
|---|---|
| PREPARE_AUDIO | 0,07 с |
| DETECT_SPEECH | 0,13 с |
| DIARIZE (pyannote 3.0 + CAM++) | 2,3 с |
| TRANSCRIBE (GigaAM v3 CTC int8) | 3,5 с |
| Загрузка LLM (1,06 ГБ в RAM) | 2,2–2,8 с |
| CORRECT_TEXT (1 реплика: промпт 275 токенов, 68 выходных) | 23,6 с (3,5 ток/с) |
| Итого, запись → готовый транскрипт | ~35 с (RTF ≈ 2,3 на сэмпле) |

Критический урок: **debug-сборка AGP не задаёт флаг оптимизации, и clang работает на
-O0** — llama.cpp в таком виде даёт ~7 с/токен (в ~25 раз медленнее). `-O2` добавлен
в CMakeLists для debug-конфига. WER до/после LLM на реальных русских диалогах A/B/C
пока не измерен — команда готовит набор; заявлять улучшение нельзя. LLM-этап доминирует
во времени; при нехватке RTF резерв — Qwen2.5-0.5B (~3× быстрее).

## Ограничения

- Фильтр галлюцинаций лексический: тонкое искажение смысла (синонимы, смена адресата)
  он не ловит — только типовые поломки.
- Числа словами («пятнадцать» ↔ «15») и даты словами не защищены отдельно.
- Контекст соседних реплик по умолчанию выключен: без замеров качества безопаснее
  править изолированно.
- Измерения на устройстве не выполнены (нет устройства); APK вырос примерно до 1,4 ГB.
