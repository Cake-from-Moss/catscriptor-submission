# Issue #5: Silero VAD → GigaAM, таймкоды речевых фрагментов

## Актуальное решение: таймкоды реплик, не слов

Официальное ТЗ Nuclear IT Hack (слайды 8, 9, 14, 15, 17) требует временные
интервалы реплик. Обязательные `TimedWord` и CTC forced alignment были ошибкой
первоначальной архитектуры, а не требованием организаторов. Они больше не блокируют
ASR. JSON остаётся строго `{"transcript":[{"speaker_id":"speaker_1","start_ms":1250,"end_ms":4380,"text":"Добрый день!"}]}`.

Контракты: `AsrSegment(time, text)` возвращает текст и абсолютный полуоткрытый
интервал обработанного аудиофрагмента; пустой текст допустим для тишины.
`TranscriptionBackend.transcribe(audio, segment)` принимает произвольный валидный
интервал записи, не только целый VAD-сегмент. `Utterance` не требует слов;
LLM меняет только текст, сохраняя интервал и спикера. `UtteranceMerger` работает
с фрагментами, а не с обязательными временными метками каждого слова.

VAD обнаруживает речь, но не гарантирует одного говорящего на сегмент. В #6
диаризация должна уточнять интервалы отдельных участников и при необходимости
повторять ASR на более коротких участках. Делить готовый текст между спикерами
по равномерным или эмиссионным «границам слов» нельзя. Финальные `speaker_N` — #6.

CTC-прототип, патч, скрипт сборки и тесты сохранены как необязательный эксперимент.
Официальный AAR и прежняя GigaAM v3 CTC остаются основным путём. Измерение точности
границ слов не входит в MVP. Результаты текущей реализации и проверок будут
приведены ниже отдельно от исторических прогонов.

## Production backend и ограничения

`SherpaTranscriptionBackend(context, numThreads = 2)` реализует `TranscriptionBackend`
через один ленивый `SherpaModelResource` и официальный sherpa-onnx 2.0.1. Пример
владения: открыть PCM → `SherpaVoiceActivityDetector.use { detect(audio) }` →
`SherpaTranscriptionBackend.use { backend -> segments.map { backend.transcribe(audio, it) } }`
→ закрыть PCM. Эти этапы выполняются вне UI; VAD освобождается до загрузки GigaAM.
Модели доступны сразу из APK, разрешения INTERNET нет.

Результат сохраняет **точно входной** `TimeRange`, а не точки эмиссии токенов.
Начальное смещение переводится в `Long`-сэмплы (`ms * 16`) с проверкой переполнения;
допускается только округление последней неполной миллисекунды файла вверх.
Реально читаемый конец ограничен числом сэмплов. Остальные выходы за файл отклоняются.
Короткие speaker-turn интервалы можно передать тем же методом без word alignment.

Речь дольше 25 секунд обрабатывается неперекрывающимися порциями до 400000 сэмплов;
чтения — не более 8192, частичные чтения собираются, невалидные PCM/ранний EOF
отклоняются. Дополнительный Kotlin PCM-буфер ограничен порцией, не длиной записи;
это не оценка полной native RAM. Тексты непустых порций соединяются пробелом.
**Ограничение:** граница технической порции может оборвать слово, контекст между
порциями не передаётся; качество стыков не измерено. Технические границы не
выдаются за VAD- или speaker-turn метки и не добавляют выдуманных реплик/слов.

Вызовы backend сериализованы. Ошибка или отмена автоматически закрывает backend;
для повтора создаётся новый экземпляр. `close()` идемпотентен, последующие вызовы
запрещены до чтения PCM. Stream освобождается в `finally`, recognizer — при close;
входной PCM остаётся собственностью вызывающего кода. Синхронный JNI не прерывается
посередине: отмена проверяется до/после, close ждёт окончания нативного вызова.
Поэтому close не вызывают на UI-потоке. Проверки lifecycle не доказывают отсутствие
всех native утечек; peak PSS/RTF здесь не измеряются.

По дополнительному запросу подключён пользовательский путь SAF → Foreground
Service → PCM → VAD → ASR → экран результата. Это **не полный конвейер**:
диаризация остаётся #6, обязательная локальная LLM — #7. Промежуточный результат
имеет статус `AsrReady` и хранит `TranscriptDocument.asrDraft`; финальные `lines`
и `speakers` пусты, фиктивный `speaker_1` не создаётся. Черновик показывает
исходные интервалы ASR без плеера, редактирования и экспорта. Строгая JSON-схема
не меняется; черновик нельзя экспортировать как финальный transcript.
Хранилище пока in-memory: после смерти процесса импорт и результат теряются.
Оценочные записи, метрики и файлы другого агента #11 не меняются.

## VAD

`SherpaVoiceActivityDetector` реализует существующий `VoiceActivityDetector`.
Он использует CPU `Vad.compute()` из официального sherpa-onnx 2.0.1 с локальной
Silero v4: ONNX имеет состояния `h/c`, вход `x`, выход вероятности и новые состояния;
экспорт k2-fsa поддерживает 16 кГц. Это не произвольная свежая Silero v5/v6.

Модель: 643854 байта. URL, размер, SHA-256 и MIT LICENSE указаны в
`assets/vad-manifest.properties` и таблице README. `prepare_models.py` проверяет
их вместе с прежним комплектом GigaAM; `verifyBundledModels` не использует сеть
и отклоняет отсутствие, неверный размер или SHA. В Git бинарные модели не входят,
но обязательны внутри APK. URL релиза изменяемый, поэтому идентичность задаёт SHA.

PCM читается порциями до 8192 нормализованных float-сэмплов. Частичные чтения
собираются в окна 512 сэмплов (32 мс), последнее окно дополняется нулями только
для инференса. Временной счётчик учитывает исходные сэмплы, а не дополнение.
Повторной амплитудной нормализации нет: `PcmAudioSource` уже возвращает [-1, 1].
NaN и выход из диапазона отклоняются. Для полностью нулевого окна вероятность
принудительно нулевая, но модель вызывается для корректного обновления состояний.

Не используется нативная очередь VAD: в v2.0.1 она хранит PCM, имеет кольцо на
60 секунд, а `maxSpeechDuration` меняет пороги и **не гарантирует** жёсткое разбиение.
`VadSegmentation` хранит только вероятностное состояние и выходные интервалы.
Счётчики сэмплов — `Long`; весь файл/речевой фрагмент в память не загружается.
Дополнительная память PCM — десятки КБ, список результата — O(числа сегментов).
Это не измерение полной RAM ONNX Runtime.

Начальные параметры, **не оптимизированные по записям**:

| Параметр | Значение | Влияние |
|---|---:|---|
| threshold | 0.5 | Выше — меньше ложных срабатываний, больше риска тихой речи |
| minSpeechDuration | 100 мс | Подавляет короткие всплески; может потерять очень короткое междометие |
| minSilenceDuration | 300 мс | Ниже — больше сегментов, выше — больше объединённых фраз |
| speechPad | 150 мс с каждой стороны | Защищает края слов, но добавляет тишину |

Продолжение речи использует гистерезис `threshold - 0.15`, строго положительный.
Уверенное начало требует непрерывного превышения threshold; окончание — достаточно
долгой вероятности ниже порога продолжения. Разрешение решений — 32 мс, не 1 мс.
Padding обрезается по началу/концу файла, пересекающиеся интервалы объединяются;
начало округляется вниз, конец вверх в абсолютные миллисекунды (`sample/16`).
Непрерывная речь может дать сегмент длиннее 25 секунд: её ограниченное разбиение
и удаление дубликатов на стыках ASR ещё не реализованы.

## Владение ресурсами и отмена

Конструкторы не грузят модели. VAD загружается лениво на `Dispatchers.IO`, через
тот же `BundledModelStore`, что ASR, с отдельным строгим манифестом. `detect()`
сериализован `Mutex`; монитор защищает native compute/load/reset/release от close.
Состояния Silero сбрасываются между записями. Ошибка/отмена освобождает VAD на
рабочем потоке; успех оставляет ресурс до `close()` владельца. Close идемпотентен,
последующее использование запрещено. Входной PCM никогда не закрывается этапом.

Порядок владельца: открыть PCM → VAD.use/detect → освободить VAD → ASR.use/decode
сегментов → освободить ASR → закрыть PCM. Это демонстрируется отдельным Android-тестом,
но **не подключено** к production-оркестратору. Для ASR не создана вторая загрузка
той же модели; диагностическая возможность расширяет `SherpaModelResource`.

Отмена проверяется между чтениями, окнами и перед/после JNI. Нативная инициализация
и decode синхронны и не гарантируют немедленного прерывания. Close ждёт фактического
возврата из нативной операции, не освобождает указатель из другого потока в decode.
Не вызывайте close на UI: ожидание может блокировать. Размер файла GigaAM
224721476 байт не равен полной RAM: нужны также ORT, активации и PCM-чанк.
Пик PSS для новых этапов пока не измерен.

## Прототип CTC alignment: что он доказывает и чего нет

Обычный `OfflineRecognizerResult` даёт текст, символьные токены и точки эмиссии,
но не конечные границы CTC-слов. Поле `durations` не заполняется для GigaAM CTC;
его наличие в общем результате других декодеров не решает эту задачу.
Проверяемые исходники тега v2.0.1:

- [Kotlin result](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/sherpa-onnx/kotlin-api/OfflineRecognizer.kt)
- [CTC decoder](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/sherpa-onnx/csrc/offline-ctc-greedy-search-decoder.cc)
- [CTC recognizer](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/sherpa-onnx/csrc/offline-recognizer-ctc-impl.h)
- [feature defaults](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/sherpa-onnx/csrc/features.h)
- [Silero implementation](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/sherpa-onnx/csrc/silero-vad-model.cc)

Отдельный патч `dependencies/patches/sherpa-onnx-2.0.1-ctc-probe.patch` экспортирует
исходный `log_probs` **того же** GigaAM Forward, до greedy decode. Передача через
существующий stream option `catscriptor.ctc.frames.v1`, без изменения Kotlin/JNI ABI.
Включается только явным запросом, максимум 625 кадров, словарь 34, blank 33,
subsampling 4. В стандартном AAR запрос явно отклоняется как неподдержанный;
молчаливой подмены alignment точками эмиссии нет.

`CtcPosterior.align()` делает Viterbi по CTC-состояниям blank/символ, сохраняет
первый и последний **занятые** кадры каждого символа, разрешает повтор одинаковых
букв только через blank. Есть ограничение размеров и проверка отмены. Это реальная
покадровая привязка к выходу модели, не распределение длительности по числу слов.
Но при target из собственного greedy decode исходный greedy-путь уже оптимален:
Viterbi не создаёт недостающую информацию о длительности звучания.

Временная сетка прототипа: feature hop 10 мс × subsampling 4 = 40 мс, как в
upstream `Convert()`. Диагностические координаты кадра k — [40k, 40(k+1)) мс;
для сегмента было бы необходимо прибавить его абсолютный startMs. Начало сетки,
эффекты feature padding и фонетическая задержка **ещё не проверены независимой
разметкой**. Конец занятой CTC-ячейки нельзя объявлять акустическим концом слова.

Словарь: SPACE=0, русские буквы=1..32, `<blk>`=33; отдельной «ё» нет, нет BPE
и пунктуационных токенов. В дальнейшем слова можно группировать по SPACE,
сохраняя пустые blank-паузы между словами; заполнять паузы вымышленными границами
нельзя. Пунктуация последующей LLM не получает новых таймкодов. Длинное слово
могло бы охватывать первый–последний кадры букв с внутренними blank; короткое
междометие может занимать один пик. Это не подтверждает длительность междометия
и конца длинного слова. Ошибка не ограничена одним шагом 40 мс: CTC-пики могут
быть смещены существенно сильнее, численная погрешность пока неизвестна.

**Блокер:** для строгого `TimedWord` требуется проверенное акустическое выравнивание.
Минимальный следующий шаг — измерить отдельно ошибки начала и конца CTC-интервалов
на независимой русской пословной разметке и сопоставить с согласованным допуском.
Неподтверждённые интервалы не публикуются. Если CTC не укладывается в допуск,
нужен согласованный эксперимент с отдельным локальным aligner. Ни контракт,
ни модель автоматически не заменяются. Отсутствие проверки не доказывает,
что CTC практически непригоден: сейчас не установлена величина его ошибки.

### Исследование отдельного aligner

Проверка первоисточников 2026-11-07; модели не скачивались и не подключались.
Готовый совместимый aligner для GigaAM-текста на Android пока **не подтверждён**.

- В исходниках sherpa-onnx v2.0.1 не найден отдельный публичный forced-aligner API
  для заданного текста. Whisper имеет attention + DTW, но это таймкоды его собственных
  токенов, не штатное выравнивание GigaAM-текста. В
  [DTW реализации](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/sherpa-onnx/csrc/offline-whisper-dtw.cc)
  последний токен продлевается до конца аудио, а при недостатке переходов возможна
  нулевая длительность. Такой результат нельзя автоматически принять за границы слов.
- [Qwen3-ForcedAligner-0.6B](https://huggingface.co/Qwen/Qwen3-ForcedAligner-0.6B)
  явно поддерживает русский, заданный текст и предсказание начала/конца слов;
  заявленный предел входа — 5 минут, лицензия Apache-2.0. В официальном
  [списке файлов](https://huggingface.co/api/models/Qwen/Qwen3-ForcedAligner-0.6B/tree/main?recursive=true&expand=false)
  `model.safetensors` занимает **1835544544 байта** (около 1,71 GiB), SHA-256 LFS
  `47831d0e82f96b20e9034dba01a075ee06436654719f6a68289e49f1b65ce0e7`.
  Это размер весов, не пик RAM. Подтверждён официальный Python/PyTorch/Transformers
  путь, но не Android CPU runtime, ONNX/GGUF-экспорт или подходящая квантизация.
  Наличие поддержки Qwen3-ASR само по себе не доказывает поддержку ForcedAligner.
- В официальном
  [Qwen aligner](https://github.com/QwenLM/Qwen3-ASR/blob/main/qwen_asr/inference/qwen3_forced_aligner.py)
  границы предсказываются через logits timestamp-позиций. Однако `parse_timestamp()`
  вызывает `fix_timestamp()`: немонотонные предсказания могут заменяться соседними
  значениями или **интерполироваться**. Нельзя молча выдавать исправленные значения
  за прямой выход модели; прототип должен сохранять исходные предсказания и явно
  отклонять неподходящие интервалы, не придумывая недостающие границы.
- Vosk выдаёт границы слов собственного lattice decode; грамматика распознавания
  не равнозначна forced alignment произвольного внешнего текста. Подтверждённого
  минимального Vosk/Kaldi-пути для выравнивания GigaAM-текста здесь не найдено.

Подключать Qwen как обычную небольшую модель в рамках #5 сейчас необоснованно:
потребуются отдельный перенос runtime/экспорт, проверка численного соответствия,
лицензий всех компонентов, памяти, скорости и ошибок границ на русской ручной
разметке. Это отдельный архитектурный эксперимент, требующий согласования.
Ни одного нового aligner в APK нет; исходная упаковка GigaAM сохранена.

### Сравнение подходов

| Стратегия | Подтверждено | Не подтверждено | Решение |
|---|---|---|---|
| A: существующая GigaAM CTC | Настоящие log-probabilities одного Forward, blank=33, символьный словарь, Viterbi с повторами через blank; дополнительных весов нет | Ошибка начала/конца слов, доверительный порог, origin/контекст кадров, качество на стыках чанков | Приоритетный кандидат для измерения; не выдавать эмиссионные интервалы за подтверждённые `TimedWord` |
| B: отдельный aligner | Qwen3-ForcedAligner заявляет русский; официальный вес ~1,71 GiB, Apache-2.0 | Подходящий Android runtime, пик RAM, скорость, точность после переноса | Не добавлять без отдельного согласования |
| C: Whisper.cpp | Русский multilingual ASR, экспериментальные token timestamps и DTW; JNI VoiceScribe возвращает сегменты | Преимущество границ на русском, Android RAM/RTF и WER относительно GigaAM | Не менять ASR на основании наличия API |

Официальный GigaAM тоже предлагает `word_timestamps=True`, но это не отдельная
модель акустических границ. На зафиксированном
[commit 7447938](https://github.com/salute-developers/GigaAM/tree/7447938d791c4f3e643386ee22c33777004293a5)
[`timestamps_utils.py`](https://github.com/salute-developers/GigaAM/blob/7447938d791c4f3e643386ee22c33777004293a5/gigaam/timestamps_utils.py)
группирует токенные эмиссии по SPACE/`▁`: начало — первый frame, конец — последний
frame + 1. Шаг вычисляется как `audio_length / sample_rate / encoder_seq_len`.
Это не доказательство фонетического origin. В Catscriptor сохраняется проверяемая
upstream-шкала 40 мс; растягивать её ради заполнения длительности записи нельзя.

### Что именно делает VoiceScribe

Проверена версия
[`8add4d8`](https://github.com/grigorevmp/VoiceScribe/tree/8add4d885a22905deaf5b46d68bb2388504b00fb):

- [`whisper_jni.cpp`](https://github.com/grigorevmp/VoiceScribe/blob/8add4d885a22905deaf5b46d68bb2388504b00fb/app/src/main/cpp/whisper_jni.cpp#L132-L133)
  экспортирует `whisper_full_get_segment_t0/t1`, **не** пословные интервалы.
- `WhisperEngine.kt` получает сегментный JSON; `OfflineTranscriptionCoordinator.kt`
  выбирает Whisper.cpp либо LiteRT/QNN и имеет fallback на Whisper.cpp. Имена
  Tiny/Base/Small/Medium предусмотрены, но это не доказательство упаковки всех весов.

### Почему `token_timestamps` Whisper не решает требование автоматически

В проверенном whisper.cpp
[`727d3e7/include/whisper.h`](https://github.com/ggml-org/whisper.cpp/blob/727d3e7666485e12450746b523bfb4e7f057cc5e/include/whisper.h#L131-L148)
обычные `t0/t1` и экспериментальный `t_dtw` — разные механизмы.
DTW записывает **точку** токена (`t_dtw`), а не пару независимо оценённых границ.
`split_on_word` управляет разбиением длинных сегментов, не акустическим alignment.

Существенный риск в
[`src/whisper.cpp:8873–8905`](https://github.com/ggml-org/whisper.cpp/blob/727d3e7666485e12450746b523bfb4e7f057cc5e/src/whisper.cpp#L8873-L8905):
неизвестные token timestamps заполняются пропорционально `voice_length` токенов;
перед этим конец предпоследнего токена приравнивается концу сегмента. Затем
границы корректируются по energy/VAD. Использовать эти `t0/t1` без аудита происхождения
каждой границы нельзя: сам runtime может подставлять распределённую длительность,
которую требования #5 запрещают. DTW не является готовым forced aligner текста GigaAM.
Русский язык поддерживается, но реальных русских Whisper-прогонов в этой работе нет.
Численные WER/RTF, ошибка границ и превосходство какого-либо варианта не заявляются.

### Минимальный путь снятия блокера

1. Подключить ARM64-телефон; подготовить независимую ручную разметку русского аудио:
   слово, начало, конец, правила обработки пауз/пунктуации и допустимая неопределённость.
2. Использовать существующий патч, сохранять полный покадровый путь и исходный текст.
   Сравнить **отдельно** ошибку начала/конца, включая короткое слово/междометие,
   паузы, повторы букв, длинные слова, тишину, смещения и стыки чанков.
3. Согласовать допустимую ошибку; проверить, можно ли выделить ненадёжные случаи
   измеримым критерием отказа. Сам факт существования CTC-пути — не confidence:
   даже одинаковые оценки всех классов допускают такой путь.
4. При подтверждении качества завершить backend на текущем контракте, ограничить
   PCM/DP-чанки, проверить дедупликацию, отмену и последовательный lifecycle на устройстве.
   Если качество неудовлетворительно — согласовать другой aligner, не скрытый fallback.

В этой итерации улучшена только диагностика невозможной CTC-последовательности:
`minimumFrames = tokens + adjacentRepeats` проверяется до DP. Добавлены JVM-тесты
максимальной трассы (625 × 1251 ячеек, без переполнения), отмены backtrace,
диагностики повторов и отсутствия confidence у равномерных scores.
Это **не** интеграционная проверка акустических границ и не полноценный backend.
