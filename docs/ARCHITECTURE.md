# Архитектура решения

## Контекст

Задача: по аудиозаписи разговора получить расшифровку со спикерами и временными метками
**полностью на устройстве**. Результат сравнивается с эталоном (WER, точность диаризации, таймкоды,
время обработки RTF) через экспорт в JSON.

Ограничения, из которых исходит архитектура:

- нет сети во время обработки, аудио и текст не покидают устройство;
- APK содержит все модели и работает сразу после установки;
- обязательна локальная LLM, которая правит текст ASR (пунктуация, регистр, ошибки распознавания),
  а временные метки остаются от ASR;
- JSON-формат экспорта фиксирован, временные метки относятся к репликам, а не к словам.

## Компоненты

Конвейер, каждый этап — отдельный модуль за интерфейсом (`domain/pipeline`):

```
Файл / микрофон
  → декодирование в 16 кГц mono PCM   (AudioDecoder: MediaExtractor + MediaCodec)
  → VAD                               (VoiceActivityDetector: Silero)
  → диаризация                        (DiarizationBackend: эмбеддинги окон ERes2Net + спектральная кластеризация)
  → ASR по ходам спикеров             (TranscriptionBackend: GigaAM v3 через sherpa-onnx)
  → слияние реплик                    (UtteranceMerger)
  → LLM-коррекция текста              (TextCorrectionBackend: Qwen2.5 через llama.cpp, JNI)
  → результат и экспорт               (TranscriptExporter: JSON / TXT / SRT)
```

| Слой | Каталог (`src/mobile/android/app/src/main/java/org/cfm/catscriptor/`) | Роль |
|---|---|---|
| UI | `ui/` | Compose-экраны: главный, список записей, расшифровка, лист экспорта, настройки |
| ViewModel | `viewmodel/` | Состояние экранов (`StateFlow`), бизнес-логики в UI нет |
| Домен | `domain/pipeline`, `domain/diarization`, `domain/app` | Контракты этапов, кластеризация, модель записи и результата |
| Аудио | `audio/`, `recording/` | Декодирование, запись микрофона, VAD-сегментация, фоновая служба обработки |
| Нативные модели | `native/models/` | Обёртки над sherpa-onnx и llama.cpp (JNI), загрузка и освобождение моделей |
| Экспорт | `export/` | JSON (`DefaultTranscriptExporter`), TXT/SRT, ZIP с аудио, share sheet |
| Приложение | `app/` | Сборка зависимостей, управление обработкой, хранилище результатов |

Тяжёлая работа идёт в foreground-службе (`AudioProcessingService`, `DiarizedDraftRunner`),
прогресс доходит до UI через `StateFlow`. Одновременно в памяти находится одна модель: она
загружается перед своим этапом и освобождается после него (`ModelResource`, `BundledModelStore`).

## Основные технические решения

**Распознавание.** GigaAM v3 CTC int8 через sherpa-onnx, русская модель. ASR запускается по
участкам аудио, каждый участок распознаётся один раз. ASR возвращает текст и абсолютный интервал
участка (из VAD или хода спикера). Пословная разметка не используется.

**Диаризация:**
1. Каждый сегмент речи VAD режется на окна 1,5 с с шагом 0,75 с; для каждого окна ERes2Net даёт эмбеддинг.
2. Спектральная кластеризация (косинусное сходство, p-pruning, лапласиан, число спикеров по
   разрыву собственных значений, k-means++ с фиксированным зерном) определяет число спикеров и метки
   окон. Для коротких записей (меньше 10 окон) используется агломеративная кластеризация с порогом
   средней косинусной близости 0,375. Мелкие и очень похожие кластеры склеиваются.
3. Смена спикера внутри сегмента VAD ставится по перекрытию окон, граница сдвигается в самую тихую
   точку в пределах ±0,4 с, чтобы не резать слово.
4. Ходы спикеров идут в ASR по отдельности. Текст не делится между спикерами по выдуманным
   границам слов.

Почему ERes2Net, а не CAM++ или готовый pyannote: pyannote + кластеризация sherpa находила 1 спикера
из 2 и 8 из 4. CAM++ на дебатах с перебиваниями давал 6 спикеров вместо 3, ERes2Net-base — верное
число на всех 9 проверочных записях (таблица в [`TEST_RESULTS.md`](TEST_RESULTS.md)).

**LLM-коррекция.** Qwen2.5 Q4_K_M, llama.cpp v0.9.0 через собственный JNI-мост, жадное декодирование,
промпт на русском. LLM возвращает только строку текста реплики, спикер и временные метки не
меняются. Защита от галлюцинаций (`CorrectionGuard`, `CorrectionReconciler`): при сомнительной правке
возвращается исходный текст ASR. Три уровня: «Выкл», «Быстрая» (0,5B), «Умная» (1,5B).

**Экспорт.** Строгий JSON сериализует `DefaultTranscriptExporter` без рефлексии; TXT и SRT строит
`TranscriptRendering`. Формат описан в [`PROTOCOL.md`](PROTOCOL.md).

**Хранение.** Записи и результаты — в приватном каталоге приложения (атомарный снимок библиотеки).

## Зависимости

| Зависимость | Версия | Назначение |
|---|---|---|
| sherpa-onnx (официальный AAR) | 2.0.1 | ASR, VAD, извлечение эмбеддингов диаризации; версия и SHA-256 в `dependencies/sherpa-onnx.properties` |
| llama.cpp | v0.9.0 (закреплён) | Запуск GGUF-модели коррекции; собирается из исходников через CMake (NDK 28.2.13676358, C++17) |
| Kotlin / Jetpack Compose / Coroutines | Kotlin 2.2.10, AGP 9.5.1 | Язык, UI, фоновая работа |
| Gson | см. `gradle/libs.versions.toml` | Запись JSON без промежуточного дерева |

Модели готовит `scripts/prepare_models.py` на компьютере разработчика. Во время работы приложения
сетевых зависимостей нет (нет аналитики, облачных SDK, Firebase).

## Безопасность и приватность

- Манифест не содержит разрешения `INTERNET`: приложение технически не может отправить данные.
- Запрашиваются `RECORD_AUDIO` (запись с микрофона), уведомления и разрешения foreground-служб.
- Записи и результаты хранятся в приватном каталоге приложения; наружу данные уходят только
  по действию пользователя: сохранение через системный диалог `CreateDocument` (без широких разрешений
  на хранилище) или «Поделиться» через `FileProvider`.
- Модели копируются из APK в `noBackupFilesDir` и проверяются по SHA-256 перед нативной загрузкой.
- Оценочные скрипты (`src/mobile/android/tools/evaluation`) работают на компьютере, не входят в APK и
  не обращаются к сети.
